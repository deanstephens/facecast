# Facecast

Walk around a sunny town square with friends, in first person. Everyone is a small hovering robot whose face is a
screen, and **your webcam is your face**: whoever walks up to you sees you on it, and hears you, louder the closer
they stand.

It's a static web page: Unity for the world, Blender for every model, and WebRTC between the browsers for video,
voice and movement. Put it on GitHub Pages (or any static host), send a friend the room's link, and you meet. There
is no game server.

- **Engine:** Unity 6000.6.0f1 (Unity 6.6), Universal Render Pipeline, Input System, UI Toolkit, WebGL 2
- **Art:** every model is generated by Blender 4.5 Python scripts (`Blender/`), coloured with vertex colours
- **Networking:** WebRTC, peer to peer, through [Trystero](https://github.com/dmotz/trystero) (signalling over public
  Nostr relays, or MQTT brokers), in the page around the Unity build
- **Targets:** web browsers (desktop Chrome, Edge, Firefox, Safari). Desktop builds run an offline preview with demo
  bots.

## Playing

Open the page, type a name, pick a colour and press **Join**. The browser asks to use your camera and microphone;
either can stay off (your face screen then shows a cartoon face that blinks and talks along). The room's name is in
the address (`…/facecast/#mint-fountain-42`): **Copy invite link** and send it to whoever you want to meet. Anyone
with the link can join, so pick a room name nobody will guess for a private chat.

| Action | Input |
|---|---|
| Look around | Click the square to capture the mouse, then move it. Esc lets go. |
| Walk | W A S D or the arrow keys |
| Run | Shift |
| Jump | Space |
| Microphone on/off | M, or the microphone button |
| Camera on/off | V, or the camera button |
| Leave | The door button |

Your own camera shows in the corner, mirrored like a mirror; everyone else sees you the right way round. Names float
over everyone's heads and light up, along with their antenna and ear lights and the rim of their screen, while they
speak. Use headphones: other people's voices coming out of speakers get back into your microphone.

**Demo bots.** `?bots=3` in the address (before the `#room`) adds up to eight strollers who chat with each other and
turn to face you. Only you see them, and they wear your own camera, which makes a quick check that your picture comes
through: `https://you.github.io/facecast/?bots=3#test`.

## Putting it on GitHub Pages

1. Create a GitHub repository and push this project to it (`origin`).
2. Build and deploy: `Tools/deploy_pages.sh --build` (or build in Unity with **Facecast ▸ Player Builds ▸ Web**, then
   `Tools/deploy_pages.sh`). It pushes `Builds/WebGL` as the only commit of the `gh-pages` branch and switches Pages on
   for that branch.
3. A minute later the game is at `https://<you>.github.io/<repository>/`.

Pages is a plain static host: it can't send the `Content-Encoding` header Unity's compressed files normally need, so the
web build uses gzip with **decompression fallback** (the loader unpacks the files itself). Browsers only allow cameras
on `https://` pages and on `localhost`; Pages is https.

**Settings without rebuilding.** `config.js` next to `index.html` (source: `Assets/WebGLTemplates/Facecast/config.js`)
holds settings you can edit on the deployed site:

- `turn`: TURN servers. Most home connections reach each other directly, but some networks (offices, schools, some
  mobile carriers) block it, and then those people can't see each other until there's a TURN server to relay through.
  Cloudflare, Twilio and metered.ca offer them, or run [coturn](https://github.com/coturn/coturn). When a connection
  fails the page says so.
- `net`: `'nostr'` (default) or `'mqtt'`: which public network browsers use to find each other. `?net=mqtt` in the
  address overrides it.
- `relayUrls`: your own Nostr relays or MQTT brokers instead of the public ones.

**Privacy.** Video, voice and movement go straight between the browsers in a room, encrypted (WebRTC). To find each
other, browsers post connection offers (encrypted with a key derived from the room name) to public relays, so pick
room names nobody will guess. Nothing is stored anywhere.

**Limits.** Everyone connects to everyone, so each person sends their camera to every other person. That's fine for
a handful of people; past about eight, upload bandwidth and decoding start to tell. Walking needs a keyboard and
mouse; on a phone you can join, be seen and talk, but not move.

## Trying it on this computer

```bash
python3 Tools/serve_web.py          # serves Builds/WebGL at http://localhost:8790
```

Open `http://localhost:8790/#test` in two windows (better: two different browsers, or one in a private window) and
join both. Both share your one camera.

**End-to-end test.** `cd Tools/web && npm install && npm run e2e` starts the server, opens two Chrome instances with
fake cameras and microphones (a moving test pattern and a beep) in a fresh room over the real relays, has one go through
the join card (typing her name, picking a colour) and the other join from the address, stands them face to face, and
checks that each sees the other's camera on their face screen and hears them. Screenshots of the card and both views
go to `Screenshots/web_*.png`. `npm run e2e -- --headed` shows the windows; `npm run e2e -- --url
https://you.github.io/facecast/` tests the deployed site.

## How it works

The page (`Assets/WebGLTemplates/Facecast/`) and the Unity build split the work:

- **The page** (`facecast.js`) loads the Unity build behind the join card, owns your camera and microphone, and joins
  the WebRTC room with Trystero. Every browser connects to every other one, sends its camera and microphone as media
  streams, and sends two small messages over a data channel: `hello` (name, colour, camera and microphone on or off)
  and `pose` (where its avatar stands and looks: six floats, 15 times a second, stamped with the sender's clock). It
  forwards both to the game (`SendMessage("Room", "OnNetEvent", json)`). Voices play through each peer's `<video>`
  element (so the browser's echo cancellation applies), with the volume set by distance.
- **The game** (`Scripts/Runtime`) is the world. `Room` turns messages into avatars. `RemoteAvatar` plays each peer's
  poses back 150 ms behind the newest, against the sender's clock (`PoseBuffer`), so movement stays smooth however
  unevenly packets arrive. `LocalPlayer` is you (a character controller and the camera) and reports your pose to the
  page through `WebBridge` / `Plugins/WebGL/Facecast.jslib`.
- **Faces.** For each peer the jslib creates a WebGL texture, which Unity wraps with
  `Texture2D.CreateExternalTexture`. Every frame it copies the newest video frame from the peer's `<video>` element
  into that texture on the GPU (`texImage2D` from the element, sRGB, flipped so v runs up), and only when there is a
  new frame. Pictures never pass through C#. The `Facecast/Face` shader crops the picture to fill the 4:3 screen
  (`VideoCrop.AspectFill`), adds a glass sheen and the speaking rim, and fades to the cartoon face when there's no
  video.
- **Keyboard.** The game listens to the keyboard on the whole page, so the page keeps key events aimed at its text
  fields away from the game (a capture-phase listener installed before the game loads).

Offline (in the Editor and desktop builds) there's no page and no network: you join at once, with three demo bots.

## Building

The scene, prefabs, materials, font and render settings are generated. In the Editor: **Facecast ▸ Build ▸ Build
Everything**. Headless:

```bash
UNITY=/Applications/Unity/Hub/Editor/6000.6.0f1/Unity.app/Contents/MacOS/Unity
$UNITY -batchmode -projectPath . -executeMethod Facecast.EditorTools.SceneBuilder.BuildEverythingBatch -logFile -
$UNITY -batchmode -projectPath . -executeMethod Facecast.EditorTools.PlayerBuilds.BuildWeb -logFile -     # → Builds/WebGL
$UNITY -batchmode -projectPath . -executeMethod Facecast.EditorTools.PlayerBuilds.BuildMac -macArch x64 -logFile -
```

After editing the Blender scripts, regenerate the models, then run Build Everything:

```bash
/Applications/Blender.app/Contents/MacOS/Blender -b --factory-startup -P Blender/scripts/build_all.py              # all
/Applications/Blender.app/Contents/MacOS/Blender -b --factory-startup -P Blender/scripts/build_all.py -- Avatar    # one
```

To update Trystero: change the versions in `Tools/web/package.json`, then `cd Tools/web && npm install && npm run vendor`.

## Tests

```bash
unity test . --mode EditMode
unity test . --mode PlayMode
cd Tools/web && npm install && npm run e2e        # the web build, two browsers, over the real network
```

EditMode tests cover pose playback (clock offsets, late and stale packets, extrapolation), video cropping, the page's
messages and launch options. PlayMode tests load the scene offline: you and the demo bots, a peer arriving, moving
and leaving through the same messages the page sends, names over heads, walking into the fountain and the outer wall,
and walking with a simulated keyboard.

**Screenshot tour.** A desktop build run with `-autocapture <dir>` photographs the square from above, then poses three
demo bots in front of you and saves your first-person view, a close-up of a face screen and a wider shot with names,
then quits:

```bash
Builds/StandaloneOSX/Facecast.app/Contents/MacOS/Facecast -autocapture "$PWD/Screenshots" -screen-width 1600 -screen-height 900 -screen-fullscreen 0
```

Other command-line options for desktop builds: `-bots N` (0–8 demo bots; default 3).

## Playing in the Editor

Press Play. Whichever scene is open, the Editor starts the game from `Plaza.unity` (the first scene in Build Settings)
and comes back to your scene when you stop. If the Editor starts on an empty Untitled scene, it opens `Plaza.unity`
instead. **Facecast ▸ Play From Start Scene** turns both off. In the Editor you're offline with three demo bots; the
network and cameras only exist in the web build.
